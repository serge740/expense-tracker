**How they work**

A passkey is a WebAuthn credential: a public/private key pair. When a user registers, their device (or password manager) creates a key pair scoped to your domain. The private key never leaves the device and is unlocked by Face ID, fingerprint, or PIN. Your server stores only the public key.

- Registration: server sends a random challenge, the device signs it with a new private key, and the server verifies and stores the public key + credential ID.
- Login: server sends a new challenge, the device signs it, and the server verifies the signature with the stored public key.
- The browser only signs for the exact domain (rpID) that registered the credential, so phishing sites can't get a valid signature. Nothing secret is stored on your server, so there's nothing useful to leak.
- Passkeys sync across a user's devices through iCloud Keychain, Google Password Manager, 1Password, etc.

NestJS service:

```ts
import {
  generateRegistrationOptions, verifyRegistrationResponse,
  generateAuthenticationOptions, verifyAuthenticationResponse,
} from '@simplewebauthn/server';
import { randomUUID } from 'crypto';

const rpName = 'MyApp';
const rpID = process.env.RP_ID!;       // e.g. 'example.com' (no scheme, no port) or 'localhost'
const origin = process.env.ORIGIN!;    // e.g. 'https://example.com' or 'http://localhost:5173'

@Injectable()
export class PasskeyService {
  constructor(private prisma: PrismaService, private jwt: JwtService) {}

  private async saveChallenge(key: string, challenge: string) {
    const expiresAt = new Date(Date.now() + 5 * 60_000);
    await this.prisma.challenge.upsert({
      where: { key }, update: { challenge, expiresAt }, create: { key, challenge, expiresAt },
    });
  }

  private async takeChallenge(key: string) {
    const c = await this.prisma.challenge.findUnique({ where: { key } });
    if (!c || c.expiresAt < new Date()) throw new UnauthorizedException('Challenge expired');
    await this.prisma.challenge.delete({ where: { key } });
    return c.challenge;
  }

  // 1. Registration (user already logged in)
  async registrationOptions(userId: string) {
    const user = await this.prisma.user.findUniqueOrThrow({
      where: { id: userId }, include: { passkeys: true },
    });
    const options = await generateRegistrationOptions({
      rpName, rpID,
      userName: user.email,
      userID: new TextEncoder().encode(user.id),
      attestationType: 'none',
      excludeCredentials: user.passkeys.map(p => ({ id: p.id, transports: p.transports as any })),
      authenticatorSelection: { residentKey: 'preferred', userVerification: 'preferred' },
    });
    await this.saveChallenge(userId, options.challenge);
    return options;
  }

  async verifyRegistration(userId: string, body: any) {
    const expectedChallenge = await this.takeChallenge(userId);
    const v = await verifyRegistrationResponse({
      response: body, expectedChallenge, expectedOrigin: origin, expectedRPID: rpID,
    });
    if (!v.verified || !v.registrationInfo) throw new UnauthorizedException();
    const { credential, credentialDeviceType, credentialBackedUp } = v.registrationInfo;
    await this.prisma.passkey.create({
      data: {
        id: credential.id,
        publicKey: Buffer.from(credential.publicKey),
        counter: credential.counter,
        transports: credential.transports ?? [],
        deviceType: credentialDeviceType,
        backedUp: credentialBackedUp,
        userId,
      },
    });
    return { verified: true };
  }

  // 2. Login (no user known yet, discoverable credentials)
  async loginOptions() {
    const options = await generateAuthenticationOptions({ rpID, userVerification: 'preferred' });
    const key = randomUUID();
    await this.saveChallenge(key, options.challenge);
    return { options, key };
  }

  async verifyLogin(key: string, body: any) {
    const expectedChallenge = await this.takeChallenge(key);
    const passkey = await this.prisma.passkey.findUnique({ where: { id: body.id } });
    if (!passkey) throw new UnauthorizedException('Unknown passkey');

    const v = await verifyAuthenticationResponse({
      response: body, expectedChallenge, expectedOrigin: origin, expectedRPID: rpID,
      credential: {
        id: passkey.id,
        publicKey: new Uint8Array(passkey.publicKey),
        counter: passkey.counter,
        transports: passkey.transports as any,
      },
    });
    if (!v.verified) throw new UnauthorizedException();

    await this.prisma.passkey.update({
      where: { id: passkey.id }, data: { counter: v.authenticationInfo.newCounter },
    });
    const token = await this.jwt.signAsync({ sub: passkey.userId });
    return { accessToken: token };
  }
}
```

Controller: four POST routes (`register/options`, `register/verify` behind your auth guard; `login/options`, `login/verify` public). `login/verify` takes `{ key, response }`.

React client:

```ts
import { startRegistration, startAuthentication } from '@simplewebauthn/browser';

// register
const optionsJSON = await api.post('/auth/passkey/register/options').then(r => r.data);
const att = await startRegistration({ optionsJSON });
await api.post('/auth/passkey/register/verify', att);

When the user taps "Sign in with passkey", the browser asks their device to verify them, and that prompt can be a fingerprint (Touch ID, Android fingerprint), Face ID, or the device PIN/pattern as a fallback. Whichever they use, they unlock the private key on their device, which signs your server's challenge.

Two things to know:

- Your server never receives the fingerprint. The biometric stays on the device and only unlocks the key. Your server only sees a valid signature.
- It works only if the device has a screen lock or biometric set up, and the user has registered a passkey on that device (or it synced to it via iCloud Keychain / Google Password Manager). Laptops without a fingerprint reader will use the PIN or a phone via QR code.

To make fingerprint the preferred method, `userVerification: 'preferred'` in the code above already prompts for biometrics when available. Change it to `'required'` if you want to force verification (no "just tap the key" without a fingerprint/PIN).

Yes, passkeys are considered more secure than passwords, and the protocol itself is solid. The remaining risk is in your implementation and your recovery flow.

**Why the protocol is strong**
- No shared secret: the server stores only a public key, so a database leak doesn't let anyone log in.
- Phishing-resistant: the browser signs only for your exact domain (rpID), so a fake site gets nothing usable.
- No password reuse, no credential stuffing, nothing to guess.
- Each login signs a fresh one-time challenge, so captured responses can't be replayed.

**Where it can still go wrong**
- Account recovery is usually the weakest link. If recovery is a weak email link or SMS OTP, attackers will go through that instead. Keep it strong and rate-limited, and notify users when a new passkey is added.
- `userVerification: 'preferred'` doesn't force a fingerprint/PIN. Use `'required'` in both registration and login if you want that guaranteed, and check `v.authenticationInfo.userVerified` on the server.
- Session handling: the passkey only proves identity at login. After that, your JWT is the weak point. Use short expiry plus refresh tokens, and prefer httpOnly secure cookies over localStorage to limit XSS theft.
- Challenges must be single-use and short-lived (the code does this). Never reuse them or generate them on the client.
- Wrong `expectedOrigin` / `expectedRPID` settings. Don't loosen these to make things work, and don't use wildcards.
- Rate-limit the `/options` and `/verify` endpoints to prevent abuse.
- Synced passkeys (iCloud, Google) are only as safe as the user's cloud account. That's still much better than most passwords, but it's the trade-off for convenience.
- The signature counter often stays at 0 for synced passkeys, so don't treat a non-increasing counter as proof of cloning by itself.

If you handle recovery well and keep sessions tight, this is a stronger setup than password login.

Passkeys are the strongest mainstream login method available (stronger than passwords, SMS, and authenticator-app codes), and WebAuthn is the same standard banks and big tech use. But the code I gave you is a solid baseline, not the maximum. To make it highly secure, add these:

**Change in the code**
- Set `userVerification: 'required'` in both registration and login, and reject if `v.authenticationInfo.userVerified` is false. This forces fingerprint/Face ID/PIN every time.

**Session security**
- Use short-lived access tokens (5 to 15 minutes) plus rotating refresh tokens.

- Rate-limit all `/auth/passkey/*` endpoints.
- Email the user when a passkey is added or removed.

- Make recovery as strong as login: time-delayed, notified, and rate-limited. Attackers target recovery, not the passkey.
- Log all auth events (success, failure, IP, device).

- Require hardware security keys (YubiKey) by setting `authenticatorAttachment: 'cross-platform'`, and use `attestationType: 'direct'` to verify the key's make and model.

**1. Serve the association files from NestJS**

```ts
import { Controller, Get, Header } from '@nestjs/common';

@Controller('.well-known')
export class WellKnownController {
  @Get('apple-app-site-association')
  @Header('Content-Type', 'application/json')
  aasa() {
    return { webcredentials: { apps: [`${process.env.APPLE_TEAM_ID}.com.yourco.yourapp`] } };
  }

  @Get('assetlinks.json')
  @Header('Content-Type', 'application/json')
  assetlinks() {
    return [{
      relation: [
        'delegate_permission/common.get_login_creds',
        'delegate_permission/common.handle_all_urls',
      ],
      target: {
        namespace: 'android_app',
        package_name: 'com.yourco.yourapp',
        sha256_cert_fingerprints: [process.env.ANDROID_SHA256!],
      },
    }];
  }
}
```

**What happens on iOS**

1. Your `app.json` declares `webcredentials:yourapi.onrender.com` under Associated Domains.
2. When the app installs, iOS fetches `https://yourapi.onrender.com/.well-known/apple-app-site-association` (through Apple's CDN) and checks that it lists `TEAMID.com.yourco.yourapp`.
3. If that matches, your app is allowed to create and use passkeys for that domain. If the file is missing or wrong, iOS silently refuses to show any credential.
4. `Passkey.register()` or `Passkey.authenticate()` shows the Face ID / Touch ID prompt. The private key is stored in iCloud Keychain, and your server verifies the signature like on the web.

On iOS the origin is `https://yourapi.onrender.com`, so `expectedOrigin` is the same as what you already have. The `android:apk-key-hash:...` origin is only for Android.
